## 🎯 核心共识

| 问题 | PM | 架构师 | 工程 Lead |
|---|---|---|---|
| **成本/可观测性缺失** | 成本必须 P0 | M1 上结构化日志 | — |
| **HITL 优先级错误** | 提到 M1 | checkpoint 是必要 | — |
| **Loop/循环可行性** | — | 当前引擎跑不通 | **最硬骨头，80% 崩盘** |
| **节点 Schema 无 SSOT** | — | 前后端状态一致性 | **10 个节点就维护不动** |
| **工期低估** | M3 1-2 月严重低估 | 平台化结构性返工 | **M1 实际 5-7 周** |
| **弃坑风险** | Go/No-Go 检查点 | — | **M1 第 4-5 周最危险** |

## 🧑‍💼 PM 评审（opus46）

### 总判：**需修改后值得做**

方向对、细节扎实，但**用户定义**和**商业化**存在结构性缺失。

### 亮点
1. 执行+数据双引脚是真差异化——比 Dify/n8n 纯数据流更能建模多 agent 协同
2. Prefab 三级机制在 agent 工作流领域尚无人做到这粒度
3. M0 Spike 极克制，700 行 mock 不碰真 LLM，工程节奏正确

### 致命问题
1. **用户画像=0**。"作者本人"不是 persona。你在给自己做工具，还是做平台？
2. **HITL + 成本统计放 P1 是优先级错误**。agent 工作流最大恐惧是跑飞了烧钱，没成本可观测没人敢上生产
3. **"从作者到平台"严重低估**。M3 一两行带过，但涉及认证/权限/计费/租户隔离——1-2 个月不够，实际 6 个月+

### 改进建议
- 补 persona（至少 2 个，带 JTBD）
- HumanApprove + 成本统计 → M1 第 3 周（能上生产的门槛）
- MVP 硬指标改为 "连续 5 天用 AgentFlow 替代纯消息流完成真实任务"
- 砍或降级"运行回放"（典型工程师自嗨功能）
- M2 末加 Go/No-Go：至少 3 个非作者用户愿试用，才启动 M3

### 追问
> **"你设想的第一个非你本人的用户是谁？他现在用什么工具？你凭什么让他切换过来？"**

#### ✅ 作者回答
> **目标用户 = 同事**，他们现在用 codex / opencode / 飞书 OpenClaw，**"看不到 agent 工作流、难以编排"是他们和我一样的痛点**。

这是一个**非常具体且可触达的 persona**——他们：
- 已经是 AI 工具的早期采用者（不需要教育）
- 痛点和作者本人同源（"看不到工作进展"）
- 社交/信任成本为零（同事直接约 demo）
- 作者就是 dogfood，反馈回路极短

**结论**：目标用户立住了，M3 平台化有了现实支撑，但**第一阶段仍以单机 + 同事局域网推广为主**，不是 SaaS 平台。

## 🏗️ 架构师评审（opus46）

### 总判：**中等偏上**

M0-M1 能落地，M2-M3 在当前架构下会结构性返工。

### 亮点
1. 执行边/数据边双轨分离是对 UE 蓝图最有价值的借鉴
2. Prefab 三级形态设计合理
3. MVP 克制得体

### 架构硬伤（每条都给了替代方案）

#### 1. "按层并行执行"过度简化（致命）
**问题**：拓扑排序的"层"基于深度，但执行边和数据边拓扑可能不同——数据在第 3 层就绪、执行边在第 5 层才到，当前设计会**死锁或提前执行**。
**替代方案**：改为**入边就绪驱动**（每个节点的所有入边就绪即可执行），参考 Prefect 或自实现 DAG executor with per-node readiness。

#### 2. Loop 节点根本跑不通（致命）
**问题**：执行引擎是纯 DAG 一次性拓扑排序，**无法表达回边/重复执行**。PRD 场景 2 的"脚本+Critic 循环"直接废。
**替代方案**：
- 选 A：**子图运行时展开**（动态 rewrite DAG）
- 选 B：**嵌套 run_workflow 执行器**（Loop 节点内部启动子 run）
- **必须在 M1 前决定**。

#### 3. HITL 暂停-恢复无持久化（中等）
**问题**：`asyncio.gather` 一把梭，进程重启 run 状态全丢。
**替代方案**：M1 至少加 **checkpoint 机制**（cache + 待审节点 ID 写 `runs/`）。

#### 4. Prefab 版本锁语义模糊（中等）
**问题**：默认 latest，但没定义 semver 兼容规则——exposed_params 改名算 breaking 吗？删 output 怎么办？
**替代方案**：强制版本锁 + migration diff + 实例升级提示。

### 被低估的复杂度
1. **Script 节点沙箱**：CPython 没有可靠的进程内沙箱，要安全必须 subprocess+seccomp 或 WASM
2. **前后端状态一致性**：Zustand 编辑态 vs Runner 运行态，断网重连/运行中编辑如何合并？现在无 CRDT
3. **文件系统 JSON 并发写入**：debounce 保存 + events.jsonl append 同目录，M1 一多会截断/脏读

### 推荐关键修改（按影响力）
1. 执行引擎：按层并行 → **入边就绪驱动**
2. **Loop 运行时语义定死**（选子图展开 or 嵌套执行）
3. **HITL checkpoint 持久化**
4. **可观测层**：M1 结构化日志，M2 上 OpenTelemetry trace
5. **Script 沙箱降级**：subprocess+timeout+ulimit+tmpdir，别搞进程内沙箱

## 📊 工程 Lead 评审（opus46）

### 总判：**勉强可执行**

计划"写给投资人看"的成分偏高。M1 往后严重低估单人 part-time 摩擦成本。Prefab Variant/Unpack、行为树节点、成本统计这些 M2 就排入，对业余项目是给自己挖坑。

### 工期现实重估

| 阶段 | 原估 | 实估 | 倍率 |
|---|---|---|---|
| M0 | 2-4h | **1-2 晚（4-8h）** | ×2 |
| M1 | 2-3 周 | **5-7 周** | **×2.5** |
| M2 | +2 周 | **+4-6 周** | **×2-3** |

### 3 个最易崩盘的点（按概率）
1. **Loop/Branch 子图执行引擎（80%）**——文档轻描淡写"第 2 周搞定"，实际最硬
2. **节点类型定义前后端双写（70%）**——没 codegen 到 10 个节点就维护不动
3. **M1 末期"跑通 demo=唯一标准"（65%）**——没测试，改一个节点默默坏三个工作流

### 被遗漏的关键任务
1. **错误恢复与状态持久化**（浏览器刷新/后端重启=全丢）
2. **节点 Schema 单一来源**（JSON Schema → Python + Inspector 的 codegen 链）
3. **前端构建工具链**（M1 必须上 Vite）

### 保命建议
1. M1 第一件事：**引入 Vite 最小构建**
2. 给执行引擎写 3 个 pytest（线性/并行/错误）——2h 投入回报无限
3. 节点定义用 JSON Schema 做 SSOT
4. Loop 节点推迟，前期用 Sequence 手动展开代替
5. 每周末打 git tag

### 停下来还债的时机
**M1 第 2 周结束必须停一次**：重构执行引擎接口、统一节点 schema、补测试——不做 M1 第 3 周接不上去。

### 最可能弃坑时间
**M1 第 4-5 周（实际日历第 6-7 周）**：新鲜感退、Loop/Branch bug 多、无测试兜底、动力归零。
